# 房市熱度摘要與歷史資料方案

狀態：階段 1–2 已實作，待 PR 審查與最終預覽驗證；階段 3–4 尚未啟用。查核日期：2026-11-10。基準為已合併 PR #3 的 `e1cb7ec`。依使用者後續授權，現已接入區域歷史、固定條件基線及描述型摘要；沒有新增每日排程或模型呼叫。

## 目標與目前缺口

讓每間房的摘要能回答「目前競爭條件如何、相較過去有何變化、哪些仍無法判定」，協助買賣策略；不以單次快照宣稱「房市逐漸回升」。Townhouse 與 SFH 保持分開，區域背景不當成主屋估值。

目前程式已具備來源、日期、成交時間線與待售 DOM，但還不能直接當成趨勢系統：

- `src/render.py:38` 依樣本數切換 90／180／365 天窗口，跨期樣本不固定。
- `src/state.py:14` 只保存成功寄送時間、已見 ID 與最新中位數，沒有完整歷次市場狀態。
- `src/run_weekly.py:73` 已保存原始回應與來源差異，可作蒐集起點；尚無完整的查詢條件版本、歷史索引或跨期判讀。
- `src/provider.py:62` 掛牌按房型與 Active／Inactive 分頁；Inactive 不能直接代表 Pending 或成交。
- 本機舊快照缺少分頁完整度及完整條件版本，不能直接回填為可比較基期。應保留為歷史觀察，經條件審計才可能採用。

用語以 [PRODUCT.md](../PRODUCT.md) 的下階段定義為準。

## 歷史資料可行性：已實測

以既有憑證對兩個目標 ZIP 各執行一次 `/markets?dataType=Sale&historyRange=36`，原始回應保存在 Git 忽略的 `data/research/market-heat/`。沒有更換服務、購買訂閱、改排程或寄信。

| 實際取得內容 | 結果與限制 |
| --- | --- |
| 月度總體歷史 | 兩區都有 2024-01 至 2026-11 的 35 個月份鍵；排除本月未完成資料後為 34 個完整月份。 |
| 按房型的歷史 | 2024-08 起可取得 SFH／Townhouse；一區各有 27 個完整月份，另一區 SFH 27、Townhouse 26，後者缺 2026-02。缺值不能補零或混用總體資料。 |
| 指標 | 含掛牌價格、來源 DOM、新增掛牌及當月曾待售數，可立即建立區域掛牌背景。 |
| 不能回答的事 | 不是成交價序列，沒有 Pending／Closed 流量或成交對最終開價比；不能單靠這組資料宣稱成交活絡或房價回升。 |

官方文件明示銷售市場歷史可追溯至 2024-01，樣本不足時可能缺漏；已實測的房型明細起點較晚，因此實際欄位覆蓋優先於文件所列最早日期。[端點文件](https://developers.rentcast.io/reference/market-statistics)

「完整月份」只表示曆月已結束，不保證供應商完整涵蓋或不再修訂。相同 ZIP、房型的開價中位數變動，也可能來自房屋組成改變，不能稱為同一房屋增值。

`medianPrice` 在此母體為待售掛牌價格；`totalListings` 是一個月中「任一時間曾待售」的房源數，不是月底庫存，不能跨月相加當獨立房屋數。`dataByPropertyType` 與 `dataByBedrooms` 是各自分組，不能拼成「特定房型且特定房數／尺寸」的統計。[欄位定義](https://developers.rentcast.io/reference/market-data-schema)

來源未提供特定指標的有效分母時，明示「有效樣本數未提供」；不能把 `totalListings` 當成 DOM 有效樣本數。當月曾待售數可另列為背景，但不代替缺少的分母。

## 來源與頻率選擇

| 方案 | 優點 | 代價及未選原因 |
| --- | --- | --- |
| 維持現狀 | 最少工作與額外請求 | 只能描述當期，不回答趨勢，未滿足目標。 |
| 只用區域歷史 | 可立即回補較長背景，不必等待每日累積 | ZIP 與全部尺寸不等於附近相似住宅；缺少本案的改價與狀態變化。 |
| 只累積每日房源 | 能逐步追蹤相同條件、同一 MLS 的變化 | 冷啟動、額外請求與缺日；無法重建尚未觀察的歷史，也不能由消失推定成交。 |
| **分階段混合，建議** | 先回補區域歷史並保存固定條件快照，再按需要提高頻率 | 必須將尺度與定義分開；每日蒐集仍需明確請求預算。 |

建議先用現有 RentCast 建立月度背景，沿用每週完整查詢累積固定條件快照。每日只抓 Active 的方案保留為第二階段選項，不在本輪啟用；它有助降低短暫改價漏看，但不能保證捕捉所有日內變動。

Redfin 區域下載可補充 Pending、成交與其他不同母體的指標，但本輪尚未驗證指定城市／ZIP、SFH／Townhouse 的實際下載資料列、穩定抓取及使用條件，因此不是首版必要依賴。其現行週資料為滾動 28 天，小地理月資料為滾動三個月；不能把相鄰發布值當獨立期間，也不能混接方法改版前後的序列。[方法](https://www.redfin.com/news/data-center/methodology/)、[下載入口](https://www.redfin.com/news/data-center/downloads/)

Zillow 公開歷史資料及 Market Heat Index 可作後續廣域背景候選；指定區域與房型覆蓋未驗證。其指數包含平台專有的買家 leads，不能聲稱以我們的掛牌快照重建同一指數。[資料入口](https://www.zillow.com/research/market-data/)、[方法](https://www.zillow.com/research/market-heat-index-methodology/)

## 請求量與費用：條件式估算

本輪完整查詢實際用了 11 次請求：兩個 AVM、分房型／狀態掛牌及房屋紀錄，包含一個需要兩頁的查詢。頁數、重跑與其他用途會改變費用；實際訂閱、當月總用量及帳單未查核。

| 頻率方案 | 假設下的每月請求 |
| --- | --- |
| 原每週完整查詢＋每月兩區歷史刷新一次 | 四／五次週報月份約 46／57 次。 |
| 再加非週報日的三組 Active 每日查詢 | 30 天四次週報約 124 次；31 天五次週報約 135 次。假設每組 Active 一頁，週報日重用該次擷取，不重抓。 |

公開 Developer 方案為每月 50 次免費、超額 $0.20／次。若只有本專案用量，以上每日例子為約 $14.80／$17 超額費用；這不是實際帳單，也不表示需要升級訂閱。更高頁數、其他請求及失敗計費規則須再核對。實作前設定明確月請求上限，不能默默改成每天執行整套 AVM／歷史掛牌／房屋紀錄。[官方價格](https://www.rentcast.io/api)

## 資料與模組邊界提案

沿用標準函式庫及 JSON 檔案，不新增資料庫、模型或文字生成服務。先將原始取得、標準化、判讀、呈現分開：

| 資料型別 | 最小責任 |
| --- | --- |
| `CohortSpec` | 固定地域、房型、房數、衛浴、尺寸、排除規則、來源／正規化版本；產生條件指紋。設定改變就換基線。 |
| `CaptureManifest` | 來源、查詢指紋、實際擷取時間、來源更新日、頁數、完成／部分／失敗、原始資料雜湊及嘗試識別。 |
| `ListingObservation` 歷史索引 | 以房屋身分、戶別、來源、MLS 及掛牌起點識別事件；分開保存當時觀察與後來回補／修正。 |
| `RegionalSeries` | 地域、房型、來源定義、月份、完成月份旗標、樣本母體與缺值；不與狹窄條件房源混合。 |
| `HeatAssessment` | `current_only`、`descriptive_change`、`mixed_signals`、`insufficient`、`stale_or_partial`；每句對應證據與不能判斷的原因。首版不產生通用熱度分數。 |

- `provider.py` 加入月度歷史取得邊界，不在 renderer 發送網路請求。
- 新 `history.py` 保存 manifest、原始快照與版本索引；使用原子寫入、單寫入者與排程識別，成功擷取重跑時重用結果，部分失敗可辨識，不能偽裝為完整。
- 新 `heat.py` 為純函式，輸入已標準化、可比較的序列與規則，輸出證據及限定文案；不讀網路、SMTP 或 `.env`。
- `render.py` 只呈現 assessment，HTML 與純文字一致。
- 蒐集成功與寄送成功分開：資料取得成功即可進歷史；SMTP 失敗不抹除歷史，正式寄送狀態仍只在寄送成功後更新。預覽只能寫預覽／研究資料，不能偷偷推進正式歷史基線。
- 月度背景屬可降級的新增依賴：取得失敗或過舊時，既有逐筆週報仍可寄送，區域摘要明示不可用／日期，不把失敗當零。請求預算優先保留既有週報，不為額外背景耗盡核心查詢額度。

查詢條件與型別命名可逆；持久化格式及指紋屬長期契約，首版必須有 schema／規則版本。不要把舊 `seen_comp_ids` 改造成歷史事件表，也不要在原檔覆蓋後來修正的值。

## 趨勢規則與不可下結論的情況

1. 當期狀況與趨勢分開。可先顯示現有筆數、待售 DOM、可核對日期及最後已知開價差；沒有跨期證據時直說尚無法判斷趨勢。
2. 區域月度比較僅用完成月份、同房型及同來源定義。預設同時列最近完整月份與去年同月；缺少其中一期不補零，不用本月進行中值比較完整月份。
3. 附近房源另用固定條件與期間；不得直接比較現有自動擴窗的報告結果。首次看見標「首次觀察」，只有可核對來源日期與完整擷取支持時，才稱新掛牌。
4. 房源消失不等於成交／撤牌；查詢截斷或失敗不等於庫存減少。每日同一 MLS 不增加交易樣本數，重掛是另一掛牌週期但仍是同一實體房屋。
5. 不把待售 DOM、上市至 Pending、上市至成交或 Time on Redfin 混算；不把最後已知開價差當最終開價比。特殊修繕／現金個案逐筆標示，不能主導一般行情結論。
6. 首版僅報有依據的指標變動與「訊號分歧」，不使用「整體房市逐漸回升」。若日後加入此類結論，須先取得交易活動／議價等不同面向的可比證據與季節背景，並以實際回放校準規則。
7. 至少三個非重疊期間、每期至少十個事件、兩種訊號一致等數字，只能是候選產品門檻，並非已證明足以判斷的標準。本輪不採為正式規則；稀少 Townhouse 不能靠混入 SFH 或偷偷擴大區域湊門檻。
8. 資料充分度以「跨期可比／樣本有限／不足」及原因說明，不給未校準的百分比信心。區域背景仍可能存在來源偏誤，不稱 ground truth。

## 摘要設計

選擇在每間房既有「本期速覽」內增補短篇判讀，而非最上方跨房混合熱度卡。前者稍有重複，但較不容易混淆主屋、房型與地域。

內容順序：房屋與房型 → 當期狀況 → 趨勢方向 → 最多三條具期間／來源／樣本的依據 → 資料充分度與限制。區域資料獨立標成「區域掛牌背景」，不混入附近成交筆數。

附近與區域每段判讀各自緊鄰資料充分度及原因，不能讓區域長歷史在視覺上提升附近小樣本的可信度。

以下純為虛構文案示例，並非目前市場判斷：

> **SFH｜本期有可核對的待售競爭資料；附近趨勢尚無法判定。** 目前 12 筆符合條件待售，RentCast DOM 中位數 21 天，納入 10／12 筆。尚無條件一致的附近基期，不推論升溫或降溫。
>
> **區域掛牌背景｜同 ZIP、同房型、最近完整月與去年同月比較。** 列掛牌 DOM、新掛牌及當月曾待售數的實際差異；這些不是成交價格或月底庫存。若缺月份，明示缺漏並停止該比較。
>
> **策略觀察：** 可比較競爭房源的停留時間與改價情況；目前證據不足以提出主屋掛牌價或買賣時點建議。

部分搜尋、資料過舊、查詢失敗、零筆、稀少樣本及訊號分歧都要有獨立文字；不靠顏色或紅綠燈表示結論。320px 手機需在摘要內就能分辨「現況、能否判斷趨勢、限制」，不必翻到資料完整度段落。

## 回歸案例

- 同一房源重複 30 個日快照，仍是一個掛牌週期，不是 30 筆成交。
- 首次取得一筆已上市兩個月的房屋，不標為今日新增。
- 其中一期只讀到頁數上限，不能宣稱房源減少或市場回暖。
- Townhouse 零筆、SFH 多筆，Townhouse 保持不足；區域多筆也不替代附近分母。
- 房型或篩選條件改變，基線失效；不由 90 天換 365 天產生價格漲幅。
- 月份缺漏與有效零值分開；來源修正分開記錄觀察日與事件日。
- 回補舊成交只標資料補充，不稱本期新增成交。
- 月度 `totalListings` 不改稱月底在售；同一房跨月不相加為新事件。
- 上市至成交含交割；來源 DOM 與最後已知開價差不混入其他定義的官方比率。
- 區域資料取得失敗時，既有週報仍可寄送並註明缺漏；不輸出假零值，不消耗超出預算的背景重試。
- 只有當月曾待售數、沒有 DOM 有效分母時，摘要不能寫 DOM 有效 N 筆。

## 規劃審查結果

PM、designer 與住宅交易視角 reviewer 已獨立讀取方案並通過，沒有阻擋事項。已採納可降級的區域依賴、指標分母不能混用、完成曆月仍可能修訂、組成變化及各尺度充分度標示等澄清。這是 AI 角色的規劃審查，不是持牌房仲認證；新摘要的實際桌面、手機與郵件檢查留待實作階段。

## 尚未做與下一步

不更換模型、不新增付費來源、不購買 MLS 權限、不啟動無人值守 Redfin 爬蟲、不請使用者逐筆輸入資料、不預測價格、不給黑箱熱度分數或自動買賣指示。先前兩次資料可行性查詢與本次完整預覽都不是每日持續蒐集。新文案只描述已核對的掛牌指標，正式版本仍須經使用者合併決定。

階段 1–2 的實作與驗證進行中；每日模式與更強方向性判讀分別受預算／資料驗證 gate 控制。這樣可以先利用已取得的歷史，而不必等待日快照才有可用的區域背景。

## 階段 1–2 的實作對應

- `regional.py` 保存及驗證月度來源／cache，包括 ZIP、schema、查詢範圍、雜湊、來源日期及凍結的完成月份。
- `capture_history.py` 保存固定條件、原始候選、資格、MLS 週期與來源修正，與寄送 state 分離。預覽只寫研究區，不能建立正式基線。
- `heat.py` 為純函式，輸出描述型區域判讀；`render.py` 將附近及區域各自呈現。
- `run_weekly.py` 取得兩個尺度的資料；區域資料或儲存損壞可降級，原有核心擷取與 SMTP 成功後才更新 state 的規則不變。
- 本次已執行完整真實預覽，共 13 次既有來源請求，其中 2 次 `/markets`；研究預覽沒有改變正式 history/state，也沒有寄出中間版本。

本節描述工作分支行為，不表示 PR 已合併、每日模式已啟動，或真實郵件客戶端已完成認證。
